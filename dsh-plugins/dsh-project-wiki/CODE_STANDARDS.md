# dsh-project-wiki 代码规范（项目宪法）

> 本文档是本项目的**强制性工程规范**，不满足即视为缺陷（P0 级）。
> 每一行代码都必须经得起同行评审、可被顶尖团队（如清华/北大软件工程课程）当作教材范例。
> 宁慢勿滥：可以接受更长的开发时间，不接受「屎山代码」。

## 0. 灵魂：为下一个维护者而写

代码的第一读者不是机器，是**六个月后的维护者**（可能是人，也可能是另一个 AI）。
所有规范以此为前提：**可读性 > 简洁性 > 性能**（除非性能是明确瓶颈）。

---

## 1. 注释语言（强制）

- **所有注释必须使用简体中文**（含文件头、函数说明、行内注释、TODO）。
- 英文注释 = P0 缺陷。标识符/类型名保留英文（代码是英文的，注释是中文的）。
- 例外：代码中引用的官方 API 名称、专有名词（Mermaid、Obsidian、DSH）可保留英文。

## 2. 注释规范（强制）

- 每个文件必须有**文件头注释**：`/** 模块职责一句话。 */` 格式，说明本文件干什么、不干什么。
- 每个 `export` 的公开函数/接口必须有 JSDoc：一句话说明用途 + 关键参数含义 + 返回值。
- 私有函数也必须有**一行注释**说明用途（除非名字自解释到极致）。
- **注释必须解释「为什么」，不是「是什么」**——代码本身已经说明是什么。
- 禁止注释掉的死代码；禁止 `// TODO` 遗留（要么做掉，要么删除）。
- 行内注释（`//`）与代码之间至少一个空格；JSDoc 用 `/** */`，普通注释用 `//`。

## 3. 架构与设计模式（强制）

### 3.1 单一职责
- 一个文件只做一件事；一个函数只做一件事。
- 函数体建议 ≤ 40 行；**例外**：纯声明/配置性函数（工具注册表、规则检查表、任务文本拼接、递归遍历）可超长，但必须职责单一、结构清晰（每步有中文注释）。
- 拆分以「职责边界」为准，不以机械行数为准：拆出的小函数必须有独立意义与命名。

### 3.2 契约与实现分离（本插件采用「契约注册 + 实现注册」双注册表工厂模式）
- `contracts.ts` 是**契约注册表**：工具的名称/描述/参数/输出/示例，单一真源。
- `index.ts` 是**实现注册表** + 装配工厂：`buildTool(contract, impl)` 把契约与实现组装成 `defineTool`。
- **禁止**在实现里重复写契约描述；禁止契约与实现漂移（改契约必须同步改实现签名）。

### 3.3 依赖方向
- 依赖只允许向下：`index.ts`（装配）→ `contracts.ts` / `io.ts` / `writer.ts` / `build.ts` / `evolve.ts` / `scanner.ts` / `mermaid.ts`（能力）。
- 禁止循环依赖；禁止能力模块反向依赖装配层。

### 3.4 纯函数优先
- 无副作用的函数（纯计算）与有副作用（IO/网络）分离；副作用函数命名体现动作（write/read/save/commit）。

### 3.5 错误处理
- 所有失败路径必须返回明确的错误信息（中文、可操作），禁止静默吞错。
- 工具执行失败：返回 `{ status: 'error', message: '中文可操作提示' }`。

## 4. 命名规范（强制）

- 文件：小驼峰（`io.ts`、`evolve.ts`）。
- 函数/变量：小驼峰（`projectTree`、`readFileBounded`）；常量：全大写下划线（`MAX_TREE_DEPTH`）。
- 类型/接口：大驼峰（`ProjectScan`、`WikiMeta`）。
- **名称必须表意**：`scanProject` 不是 `scan`；`buildTaskText` 不是 `task`。

## 5. 类型安全（强制）

- 禁止 `any`；禁止 `@ts-ignore`；禁止非空断言 `!` 泛滥（只允许在确凿的收窄点）。
- 所有边界输入必须显式校验（路径穿越、空串、超长）。
- 精确可选属性（`exactOptionalPropertyTypes`）必须遵守：`undefined` 不显式传。

## 6. 代码风格（强制）

- 2 空格缩进；单引号；语句无分号（与 DSH 仓库一致）。
- 每行 ≤ 120 字符；过长表达式拆行。
- 导出一律放文件末尾或具名导出，禁止默认导出（保持可追踪）。

## 7. 提交规范（强制）

- 提交信息：`类型(模块): 中文描述`（类型：feat/fix/refactor/docs/test/chore）。
- 一个提交只做一件事；不混入无关改动。

## 8. 代码审查门禁（强制，作为生成后立即校验）

每次代码生成/修改后，必须立即执行以下检查，全部通过才算完成：

```bash
# 1. 注释语言检查：英文注释必须为 0
node scripts/check-comments.mjs   # 见 scripts/check-comments.mjs

# 2. 类型检查
node node_modules/typescript/bin/tsc --noEmit

# 3. 单元测试
node node_modules/vitest/vitest.mjs run

# 4. 构建
node node_modules/tsdown/dist/run.mjs
```

### 审查清单（人工/复审用）

- [ ] 所有注释为简体中文，解释「为什么」
- [ ] 无死代码、无注释代码、无 TODO 遗留
- [ ] 单一职责：文件/函数职责单一
- [ ] 契约与实现不漂移
- [ ] 无 any / 无 @ts-ignore / 无未校验边界
- [ ] 错误路径有中文可操作提示
- [ ] 命名表意、风格统一
- [ ] 提交信息符合规范

## 9. 验收标准

- 「能否作为教材范例」= 以上 1-8 全部通过，且任意一个陌生人（人或 AI）无需提问即可读懂每个文件。
- 自检失败 → 立即修复 → 重新走完门禁 → 才算完成。
