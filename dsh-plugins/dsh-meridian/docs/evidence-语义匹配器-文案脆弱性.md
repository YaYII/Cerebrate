# 意图匹配的文案脆弱性：真实语料反证实验

> 实验脚本：`scripts/exp-semantic-ruler.ts`（可复现，一条命令）
> 结论一句话：**现行 `labelContains` 子串匹配在「同一业务事实、不同日志文案」上会静默失效；
> 语义判定在同一批场景上全部正确。** 这是「标尺需要语义匹配器」的可复现证据。

## 一、问题：语义判断被硬编码成字符串包含

`src/features/ruler.ts` 的 `FactMatcher` 只有三个条件，其中承担主判定力的是 `labelContains`：

```ts
if (matcher.labelContains !== undefined && !event.label.toLowerCase().includes(matcher.labelContains.toLowerCase())) {
  return false
}
```

`src/packs/dsedtIntent.ts` 因此不得不把**业务语义判断**写死成日志文案子串，作者甚至留下了注释解释为什么：

| 意图声明 | 硬编码子串 | 它实际想表达的语义 |
| --- | --- | --- |
| `核验成功-主档收敛`.appliesWhen | `'核验完成:'` | 这是**核验写流程**，不是读流程/幂等短路 |
| 步骤「核验完成(成功)」 | `'verified=true'` | 核验业务上通过了 |
| 步骤「主档落库」 | `'主档'` | 主档已收敛落库 |
| 噪音白名单 | `'异步落库入队失败'` 等 6 条 | 这些是环境噪音，不算业务偏离 |

原文注释（`dsedtIntent.ts` 第 30-34 行）说明了这个判断有多难：

> 仅凭 `verified=true` 会误命中两条**本就不写主档**的路径——
> 商户查询 `核验结果命中缓存: refId=…, verified=true`（读流程）
> 幂等重复 `核验命中结果缓存: verified=true`（缓存短路，不重复收敛）
> 两者都会被判成 failed/漏做「主档落库」，属**假阳性**。

也就是说：**一个纯语义的三分类问题（写流程 / 读流程 / 幂等短路），被压缩成了一种子串比较，
靠「`核验完成:` 是完成服务在写流程里独有的行」这种脆弱巧合来兜住。**

这与本项目已根治的另一个缺陷是**同一类问题**，只是提高了一层：
原来「日志格式硬编码进解析代码」导致真实测试态日志 0/144 命中；
现在「业务语义硬编码进匹配代码」会导致**日志文案一改，意图就静默失配**。

## 二、实验设计

用真实语料（产自 `tests/liveTraffic.spec.ts` 的真实流量行）构造 5 个场景，
对**同一个意图**分别跑两种匹配器，与人工确认的标准答案比对：

| # | 场景 | 标准答案 | 文案处理 |
| --- | --- | --- | --- |
| A | 核验写流程成功 | 写流程，主档步骤 = e2 | 未改写（真实语料） |
| B | 商户查询命中结果缓存 | 非写流程（应跳过） | 未改写（真实语料） |
| C | 幂等重复被缓存短路 | 非写流程（应跳过） | 未改写（真实语料） |
| D | 同一写流程成功 | 写流程，主档步骤 = e2 | 轻度改写：`confirm 完成 - ` / `主档 converge` |
| E | 同一写流程成功 | 写流程，主档步骤 = e2 | 重度改写：`verification passed` / `master record converged` |

两种匹配器：

- **确定性匹配器**：复刻 `ruler.ts` 当前的 `labelContains` 子串语义（与线上等价）；
- **语义匹配器**：把同一意图交给 TypeSafe System One（Jev）做两次结构化判定——
  一次 `Noul` 判「是否属于核验写流程」（替代 `appliesWhen` 门槛），
  一次 `Choice` 在候选事件中选出「主档落库」步骤（替代 `labelContains` 步骤匹配）。

关键点：**D、E 的业务语义与 A 完全一致**，变的只有日志文案——这正是真实重构、
加注释、换日志框架时会发生的漂移。

```bash
node --import tsx scripts/exp-semantic-ruler.ts
# 密钥：TYPESAFE_API_KEY 或 ~/.credentials/typesafe-api-key（单一来源，600）
```

## 三、实测结果（2026-09-22）

```
【写流程成功（真实语料）】      确定性 ✅  语义 ✅  noul=0.69 → in-scope，choice=e2（confidence=1.00）
【读流程命中缓存（真实语料）】  确定性 ✅  语义 ✅  noul=0.02 → out-of-scope，choice=none（0.99）
【幂等缓存短路（真实语料）】    确定性 ✅  语义 ✅  noul=0.02 → out-of-scope，choice=none（1.00）
【写流程成功（轻度改写）】      确定性 ❌  语义 ✅  noul=0.86 → in-scope，choice=e2（confidence=1.00）
【写流程成功（重度改写）】      确定性 ❌  语义 ✅  noul=0.78 → in-scope，choice=e2（confidence=1.00）

确定性匹配器（现行 labelContains 子串）：3/5
语义匹配器（TypeSafe Jev 结构化判定）：   5/5
```

三个值得记录的细节：

1. **失败方式是「静默跳过」而不是报错**。D、E 场景下 `appliesWhen` 未命中，
   标尺判 `out-of-scope` —— 一个**看起来完全正常**的结论。写流程的真实偏离从此不再被告警。
   这与本项目 §4 铁律「失败必显式」正面冲突：**这里失效了，却没有任何机制告诉我它失效了。**
2. **Choice 的 `probabilities` 正好提供了「候选间比较」**。Skill 指出 Choice 的分布
   用于比较竞争选项——本实验里 B/C 场景 `none` 拿到 0.98/0.99，A/D/E 场景目标事件拿到 1.00。
3. **Noul 的绝对概率比 `appliesWhen` 的布尔值信息量大**。B/C 得 0.02（明确非写流程），
   A 得 0.69、E 得 0.78 —— 门槛判定不再是非黑即白的子串命中。

## 四、这说明了什么、不说明什么

**说明**：在「同一业务事实、不同日志文案」的漂移下，子串匹配会静默失效，语义判定不会。
这为「标尺引入语义匹配器」提供了可复现依据，与项目已有的「原解析器 0/144 命中」反证测试同一性质。

**不说明**：语义匹配器不是确定性匹配的替代品。纯计算、精确查找、格式解析仍应留在代码里
（Skill 的原则：**code owns the workflow，模型只提供可编程的常识**）。
合理的形状是**分层**：

| 判断类型 | 归属 |
| --- | --- |
| 日志格式解析、事件 ID、顺序、耗时统计 | **确定性代码**（已实现，保留） |
| 相位（phase）、级别（level）等结构化字段 | **确定性代码**（已实现，保留） |
| 「这段运行日志是否属于某个业务场景」 | 语义判定（`appliesWhen` 的语义替代） |
| 「哪个事件在业务上体现了某一步骤」 | 语义判定（`labelContains` 的语义替代） |
| 漂移检测：同一意图的判定结果是否发生变化 | 确定性代码 + 语义判定组合 |

**成本量级**（实测）：单次调用约 2.0–3.7 秒，输入 608–670 tokens、输出 60–69 tokens。
应按「意图 × 案例」批处理调用，而不是逐事件调用。

## 五、后续可选方向（未实施，待定）

1. **语义匹配器作为 ruler 的可选后端**：`FactMatcher` 增加语义分支，
   `labelContains` 保留为快路径（零成本、离线可用），语义分支用于漂移兜底；
2. **漂移哨兵**：对同一意图的确定性判定结果做指纹，判定结果突变时告警
   （复用本项目 `features/fingerprint.ts` 的思路），把「静默失效」变成「显式告警」；
3. **语义编排层**：由 Skill 的 patterns（route / select / evidence / verify-and-escalate）
   设计更完整的判定编排，而不是逐点替换子串。

> 本实验只做了「证据收集与理解」，未改动 `ruler.ts` 的任何线上行为。
